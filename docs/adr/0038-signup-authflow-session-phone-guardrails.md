## Contexto (verificado live 2026-06-05, proyecto `bzeoszympkkicwlfdtcn`)

El spec `2026-06-05-signup-cluster-design` marco SIGNUP-session-bug / SIGNUP-phone / SIGNUP-guardrails como DESIGN-ONLY (mutan `auth.users`, R22-critico, requieren E2E). Bajo ADR-0033 (overnight build atendido) Jaime **descopo SIGNUP-formula** (091 ya lo cubrio; la mayoria de empleados ya trae su `employee_code` de Spectrum) y pidio **construir los tres blockers de signup de verdad**, con calidad via review + gate, marcando login/sesion para su E2E.

Hechos que reformaron el build (re-verificados live):

- **`completeOnboardingAction` corre enteramente sobre el client admin/service_role**, que NO escribe cookies de auth -> tras onboarding el usuario rebota a `/login` al entrar a `/perfil` (el guard `(authenticated)` no halla sesion). El client cookie-bound de `@supabase/ssr` (`createSupabaseServerClient`) ya existe y su `setAll` escribe el cookie; en un **Server Action** `cookieStore.set()` SI persiste (verificado via Context7).
- **El aprovisionamiento minteaba por `[target_field]` ∈ {email,phone}** (`createUser({phone})`) pero el login era email-only (`signInWithPassword({email})`) -> cuentas phone-only serian permanentemente no-logueables. **Live: 1 cuenta auth humanOS, email-based; 0 phone-only** (prevencion, no migracion).
- `hr.find_auth_user_by_identifier(p_field, p_value)` existe (matchea email o phone exacto, SECURITY DEFINER `search_path=''`). NO existe `hr.resolve_login_identifier` (confirmado via `pg_proc`).
- `hr.check_invite_code_rate_limit` esta keyed `(invite_code_id, ip)` -> **NO cubre login** (guardrail #5). Su tabla `hr.invite_code_attempts` da el patron a espejar.
- Guardrails ya shippeados: **#3** (invite CSPRNG `randomInt`), **#7** (commitment-hash `validated_delivery_target_hash` + re-check en completion). `people_code_ci_unique` (091) da la garantia CI que la resolucion de login necesita. `/forgot-password` ya es email-only (#6).

## Decision

1. **SIGNUP-session-bug — onboarding establece sesion en el branch new-user (A4).** Tras exito del RPC `complete_onboarding_writes`, el branch que mintea cuenta nueva hace `createSupabaseServerClient().auth.signInWithPassword({email: authEmail, password})` sobre el client cookie-bound -> aterriza autenticado en `/perfil`. La sesion se mintea **solo tras exito del RPC** (A4: un onboarding rollbackeado nunca deja sesion usable). Si el auto-login falla (caso raro), la cuenta queda correctamente aprovisionada y se redirige a `/login` (no se rollbackea: no es fallo de onboarding). La semantica compensatoria de rollback del path de fallo del RPC se preserva intacta.

2. **Branch merge cross-app -> redirect-to-login, no auto-sesion (A6).** Cuando `find_auth_user_by_identifier` halla una cuenta de otra app de ICONSA, se agrega `humanOS` a `allowed_apps` (write scoped a UN usuario resuelto, spread `...existing` preserva las apps ajenas — R22) y se redirige a `/login?merged=1` con aviso `role=status`. **No se eleva una sesion cross-app silenciosa** (conservador, R22-safe, exactamente la superficie del incidente 2026-05-25). El password tecleado se sigue ignorando en este branch (guardrail #8 / anti-enumeracion).

3. **SIGNUP-phone — email es el identificador canonico de `auth.users`; sin cuentas phone-only (A5).** El aprovisionamiento mintea SIEMPRE por email. Si `target_field='phone'`, se deriva un **email sintetico no-ruteable** `<seed>@no-mail.iconsa.local` (seed estable = `employee_code` o digitos de cedula; `.local` reservado RFC 6762 -> no enrutable) para que toda cuenta sea logueable por email+password. El telefono queda como dato de contacto del invite, **nunca** identificador de login. `find_auth_user_by_identifier` se sigue usando por phone SOLO para el lookup de merge cross-app — nunca para mintear phone-only. `email_confirm=true` al mintear (la posesion ya se probo out-of-band con el invite-code, guardrail #2; el sintetico no es ruteable para confirmar). Phone-as-login / OTP queda **post-MVP**.

4. **Login resuelve email O employee_code (SIGNUP-phone, paridad de login).** `hr.resolve_login_identifier(p_identifier text) RETURNS text` (SECURITY DEFINER `search_path=''`, service_role-only) mapea email|`employee_code` (CI via `upper()`, indice `people_code_ci_unique`) al email canonico de la cuenta `auth.users` (solo `auth_id IS NOT NULL` + `allowed_apps ? humanOS`). El form de login pasa de `email`(type=email) a `identifier`(type=text). El `employee_code` es **USERNAME, nunca credencial** (guardrail #1): solo mapea a email; el password se valida aparte en `signInWithPassword`.

5. **Guardrail #4 — anti-enumeracion en login.** `resolve_login_identifier` devuelve email|NULL **uniforme**; el login emite UN solo error generico ("Correo/codigo o contrasena incorrectos") para credencial-mala Y no-resuelve. Sin oraculo "existe / no existe", sin codigo/cedula en errores/URLs/logs.

6. **Guardrail #5 — rate-limit de login.** `hr.login_attempts` (keyed `(identifier_hash, ip)`) + `hr.check_login_rate_limit(identifier_hash, ip, ...)` (SECURITY DEFINER `search_path=''`, service_role-only) espejan el limiter de invite pero para el endpoint de login. La app pasa `identifier_hash = SHA256 hex` del identificador normalizado — **nunca el valor en claro** (R13 / minimizacion Ley 81). RLS **fail-closed**: policy RESTRICTIVE deny-all anon/authenticated; escritura solo via la RPC DEFINER + service_role. COMMENT en tabla + todas las columnas.

7. **Guardrail #1 — politica de contrasena centralizada.** `passwordPolicySchema` (Zod): >=10 chars, >=1 letra, >=1 numero/simbolo, sin espacios extremos, Unicode-aware. `Step4Schema` la reusa. El leak-check (pwned) lo hace Supabase Auth server-side (`weak_password`); NO se implementa diccionario propio.

8. **Guardrails #2 + #9 — single-use + expiracion del invite enforzados en BD (mig 093).** El invite-code es el secreto load-bearing de activacion (guardrail #2: code+cedula solos NUNCA activan; la posesion out-of-band del invite es el factor). Antes, el single-use y la expiracion se "enforzaban" SOLO en la capa app: `completeOnboardingAction` lee `consumed_at`/`expires_at` ANTES de mintear, y la consumicion real (un UPDATE condicional con `COALESCE`) era un **no-op silencioso** cuando el invite ya estaba consumido por otro auth o expirado — dejando commitear todos los demas writes (TOCTOU race + sin enforcement de expiracion en la RPC). El fix agrega un **guard atomico al inicio de `hr.complete_onboarding_writes`** (mismo patron L1 que el guard SEC-CONSENT, ADR-0035) que `RAISE` (abortando toda la transaccion, ANTES de cualquier write sensible) si el invite no existe / no corresponde a la persona / esta expirado / fue consumido por OTRO auth. `FOR UPDATE` serializa submits concurrentes. Idempotente para el MISMO `p_auth_id` (double-submit del propio usuario). Single-use + expiry quedan asi enforzados a nivel BD, race-proof y no-bypasseables por ningun POST alcanzable — el check app-level pasa a ser defense-in-depth para UX. Sin cambio de firma de la RPC -> grants y el tipo TS intactos.

9. **Aditivo, no destructivo (R22).** Los unicos writes a `auth.users` son `createUser` (una fila nueva, `allowed_apps=['humanOS']`) y `updateUserById` (merge scoped a un id resuelto, preservando apps ajenas). Sin DELETE/UPDATE masivo. Las migraciones 092 y 093 son additivas: 092 no toca `auth.users` ni datos de `hr.people` (agrega un resolver + tabla de rate-limit con RLS fail-closed); 093 solo re-define `complete_onboarding_writes` agregando el guard (no muta datos, no cambia firma).

## Triaje de los 11 guardrails

- **DONE en este build:** #1 (password Zod), **#2 (single-use del invite enforzado en BD, mig 093)**, #4 (anti-enumeracion login), #5 (rate-limit login), **#9 (expiracion del invite enforzada en BD, mig 093)**.
- **Ya estaban (preservados):** #2 capa app (invite = factor de posesion out-of-band; code+cedula solos no activan; commitment-hash) — mig 093 lo eleva a invariante transaccional de BD, #3 (invite CSPRNG + `regenerate_invite_code` expira previos no-consumidos), #6 (reset email-only en `/forgot-password`, ya anti-enumeracion), #7 (commitment-hash), #8 (merge ignora password tecleado).
- **DEFER (flagged):** #9 tuning fino del TTL (el valor 30d sigue; la *expiracion* ya se enforza en BD — lo diferido es solo acortar el TTL), #10 (bulk Spectrum->auth con R22 gate + snapshot — fuera de esta slice), #11 (CHECK formato DGI de `national_id` + formato estricto de `employee_code` — datos sucios primero, ADR-0036).

## Alternativas rechazadas

- **Merge branch auto-minteando sesion cross-app** (signInWithPassword con el password tecleado): rechazado por A6 — el password de la cuenta ajena no es de confianza, y elevar sesion cross-app silenciosa es la clase exacta del incidente 2026-05-25. Conservador > conveniente.
- **Mantener phone como identificador de `auth.users`** (con login phone+OTP): rechazado para el MVP — requiere infra OTP (Twilio) no presente; el email sintetico hace logueable a todos por un solo path hoy. OTP queda post-MVP.
- **Resolver login parseando `full_name`/cedula**: rechazado — el identificador resuelve solo por email o `employee_code` (índices existentes); cedula nunca es identificador de login (es semi-publica, guardrail #4/#11).
- **Mass-mutar `auth.users` para normalizar phone-only existentes**: innecesario (0 filas) y prohibido por R22; la solucion es prevencion en el aprovisionamiento.

## Consecuencias

- Onboarding new-user aterriza autenticado; obreros sin buzon loguean con `employee_code` + password (email sintetico interno).
- Login soporta email|employee_code, con rate-limit y respuestas no-enumerantes.
- **Pendiente de E2E de Jaime** (login/sesion no autoverificable autonomamente): (a) happy new-email aterriza autenticado en `/perfil`; (b) obrero email-sintetico logueable por employee_code; (c) merge preserva `allowed_apps` de app ajena y redirige a `/login?merged=1`; (d) fallo del RPC no deja sesion y dispara rollback; (e) ninguna fila phone-only se crea; (f) rate-limit bloquea tras N intentos.
- **Single-use + expiracion del invite ahora son invariantes de BD** (mig 093): aunque un atacante alcance `complete_onboarding_writes` por un POST alterno con un invite stale/expirado, la transaccion aborta entera (no quedan writes parciales). El check app-level read-before-mint se mantiene para UX, pero ya no es la unica linea de defensa.
